# framework-upstream

流程与命令以 [框架源码同步与反馈](../../../docs/product/framework-upgrade.md) 为准。先判定当前是框架仓库还是派生应用；派生应用通过 project.provenance.json 找上游和初始来源，通过 framework:check 获取模板，再按指南用 Git 共同祖先确认当前已合入的提交，不把应用 VERSION 当作框架版本。

## 疑似通用缺陷

1. 保留已有工作，读取最小相关实现与测试。区分配置/依赖问题、业务定制问题、框架通用缺陷与待确认；文件位于框架目录只是线索。用干净框架或最小派生项目复现，无法复现时保留不确定性，不直接归责上游。
2. 若需先修复本地应用，将通用补丁与业务功能分开，补能复现缺陷的回归测试并运行受影响检查。隔离复现、最小补丁和反馈草稿放 build/ 或仓库外；不把业务数据和完整重命名仓库当作上游复现。涉及提交时遵循当次授权与英文消息规则。
3. 按指南的反馈模板整理根因、来源/模板提交、复现、补丁、兼容影响和实际验证。已有 Issue/PR 则关联，未提交就标为草稿。公开 Issue/PR、推送或通知维护者沿用用户已有授权；缺少外发授权时交付本地草稿并继续完成可做的本地修复，不因等待上游停下无关业务开发。漏洞走上游私密渠道。
4. 准备上游修复时，在独立的干净框架分支/Fork 重做最小补丁及测试，复核产品身份、Go module 与数据库命名空间；不将派生项目的名称、凭据或业务需求带入框架。

## 同步正式修复

先确认修复已进入已发布的 framework-template；只在 dev、main 或 PR 出现不能当作下游已可获取。按任务范围检查差异，在干净的应用升级分支运行 framework:check / framework:sync；不在纯排查任务中顺带合入无关框架更新。

冲突在工具打印的隔离 worktree 内逐文件解决，然后 --continue；不需要本次结果时 --abort。保留业务意图、产品身份和本地临时补丁，不能批量选择一边或强拼无共同祖先的历史。同步后逐项核对临时补丁是否仍需要，运行 make docs、make test 与受影响构建；源码备份不替代数据库备份。

## 交付

说明问题归属及证据、本地补丁和验证、反馈草稿位置或真实 Issue/PR、上游修复与模板发布状态、下游是否已同步及剩余冲突。AI 可以协助复现、整理和合并；没有观察到的外发、合并、模板发布或目标系统结果不得标为完成。
