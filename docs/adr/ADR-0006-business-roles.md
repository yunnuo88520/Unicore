# ADR-0006：业务角色编辑与受限委派

状态：接受 · 日期：2026-10-26 · 作者：yunnuo / ymz@ebox.vip

M2d 补齐 web-platform 的业务角色创建、改名、赋权、删除与用户关联。权限仍使用 User → UserRole → RolePermission → Permission，领域 Core、CLI、桌面和 Web 单机不引入身份依赖。沿用现有用户接口的一次一个角色关联；多角色合并编辑不在本增量范围。

内置 super_admin/user 不允许改名、编辑权限或删除，避免应急管理入口及公开注册的默认权限发生变化。角色权限目录由 platform 定义；roles:write、users:update 和 settings:write 属于核心身份操作，只有超管可执行，不允许赋给业务角色。其他现有权限可分配，默认不勾选。角色列表需 roles:read，角色写入同时要求 roles:write 与真实 super_admin 关联。

新增用户仍需 users:create。非超管创建账号时，只能分配权限集合包含于自己当前权限集合的业务角色或普通用户，不能授予 super_admin。角色名称选项接口仅返回名称、ID、是否可分配，不返回权限映射；用户查看/创建/更新权限之一可读取。用户启停及角色更换仍只限超管，最后一个启用超管继续受保护。

角色写入、用户创建/关联/启停都持有已有安装行锁，在事务内重新加载操作者状态与权限，防止鉴权后发生降权仍可继续写入。角色权限或名称修改在同一事务撤销关联用户的全部 session、旧长链接、数字验证码与待发邮件。登录后的每个受保护 API 仍实时读取权限，不把旧前端菜单视为授权。

已有用户关联的角色不能删除，必须先在用户管理中更换角色。角色编辑与用户关联使用相同锁，删除和分配并发时最多一方成功，不产生悬空关联。保存传完整 name/permissions，缺失、未知、重复或受保护的权限拒绝；空数组明确表示不授予任何管理权限。名称为 1–64 个字符，不含首尾空白/控制字符；角色 ID 不变。审计只记录操作者、动作与角色 ID。

平台增加 0005，仅以幂等 DML 登记 roles:read/roles:write 并授予已有超管，不更改历史迁移 checksum、不覆盖旧业务授权。新库安装 seed 兼容预置权限；单机/桌面仍停留 framework 迁移。SQLite、PostgreSQL、MySQL 使用同组迁移、委派、撤销及并发测试；真实页面覆盖两种视口、浅深主题、键盘操作与只读账号。

安全边界：实例配置写权限覆盖 SMTP、账号恢复和安全策略，可能被用于间接接管账号，因此与身份/角色写入一样只属于超管。HTTP 公共鉴权会对目录中的不可委派权限再次验证真实超管关联，即使历史数据意外存在此类 grant 也不能绕过。
