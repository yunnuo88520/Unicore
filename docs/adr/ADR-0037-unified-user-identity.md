# ADR-0037：统一账号与多角色工作台

状态：采用。仅面向未发布框架的新安装，不提供双身份数据库的兼容或数据迁移。

## 背景与决策

应用通常需要为现有用户直接增加一到多个业务、部门管理或运营角色。独立管理员账号要求同一个人重复维护密码、资料、验证器和会话，不适合这一使用方式。本决策取代 ADR-0014、ADR-0016、ADR-0033、ADR-0034 中的独立账号与跨身份域角色限制；工作台独立构建、权限契约和超级管理员保护保留。

- 账号唯一存于 `unicore_users`，角色关联唯一存于 `unicore_user_roles`。会话、密码恢复、邮箱挑战、个人资料、TOTP、企业绑定及 OIDC 流程共用一套表。用户名、邮箱与手机全局判重。
- 两个 Web 入口继续存在，`identity_realm` 表示当前工作台。两端共用 `unicore_session`；登录、退出、改密、停用、角色或权限变化对同一账号生效，跨标签页的缓存失效信号共用一个 scope。文件、头像与个人笔记均使用 `user` 资源归属，不因访问路径改变所有者。
- 创建与修改账号支持 `role_ids` 完整集合（1–64 项，禁止重复和未知 ID）；更新时省略表示保留。旧 `role` 仅作单角色简写，不可与 `role_ids` 同时提交非空值。创建省略角色使用内置 `user`，公开注册和企业 JIT 不能指定角色。
- 多角色权限、菜单、动作与 API 授权分别取并集。角色可以组合业务与管理权限；角色 `realm` 仅保留为工作台分类元数据，不限制账号分配或授权范围。前端使用统一角色目录与多选账号表单。
- 每个 API 仍校验契约权限点、适用的 operation grant、CSRF/Origin 和超级管理员保留策略。菜单入口不授予 API。`role_ids` 变更必须由超级管理员执行；普通用户编辑者只能创建默认成员、修改状态或保留原角色，不能借用户编辑提升权限，也不能修改超级管理员账号。
- `super_admin` 可与其他角色并存，始终拥有目录全部权限；最后一个启用超管及最后一个有本地密码的超管保持事务保护。关键管理权限在事务中再次校验超管资格。
- 账号安全策略按实际管理权限选择严格的管理会话时限和强制 2FA，不能通过用户登录入口绕过。管理密码恢复仍是实例所有者的离线操作。
- 部门和岗位适用于所有账号。角色数据范围按已有并集规则解析：self、dept、dept_and_below、custom、all；all 指统一账号集合，包含具有管理角色的用户，业务按自己的数据敏感性决定是否允许授予 all。

## 新安装与验证

直接调整 SQLite、PostgreSQL、MySQL 的新安装 SQL 并重新生成 Catalog checksum；不创建独立管理员表。旧开发数据库须另建空库，不能把旧账本当成新数据库继续启动。本分支不负责数据导入、合并、旧版本回滚或线上升级。

验证覆盖共享账号和会话、全局唯一性、多角色并集、非法集合原子拒绝、阻止提权、角色撤销、最后超管保护、密码与 MFA 流程、跨工作台资源归属、迁移生成及非平台构建。数据库方言实测结果以本次实际执行为准。

内置 user 是公开注册与企业 JIT 的默认角色，只允许业务权限与本人数据范围；管理权限通过额外自定义角色授予，不能把默认注册角色改成管理角色。

离线 admin list 与默认管理员密码恢复按实际管理权限筛选统一账号；普通成员不会影响唯一管理员的自动选择。旧 sessions revoke --realm 参数仅作为兼容工作台别名，实际撤销共享账号会话。
